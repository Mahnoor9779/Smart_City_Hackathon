01

Seven decisions everything else depends on

Make these before the first commit. Each one removes a whole class of later disagreement, and every later section assumes them. If you change one, the sections downstream change with it. That is what the consistency section exists to catch.

ADR-1
Grid

H3 hexagons at resolution 8 are the universal join key. Population, air quality, land surface temperature, citizen reports, travel times. Every dataset resolves onto the same hex grid before anything else touches it. Union council and district figures are aggregations over hexes, never separate pipelines.

Lahore district is roughly 1,770 km² and an H3 res 8 cell averages about 0.74 km², so the whole district is around 2,400 cells, small enough to ship as a single payload and recompute in the browser. Drop to res 9 for your one focus union council when you need finer detail. Without a shared grid you will write the same spatial join four times and get four slightly different answers.
ADR-2
Two clocks

A cold path and a warm path, never mixed. Cold is build time: heavy geoprocessing runs on a laptop, outputs versioned artifacts, and never runs again during the demo. Warm is request time: small, cached calls to live feeds.

Nothing slow, rate limited, or network dependent may sit on the critical path of a judge clicking a button. This single rule is what stops a throttled Overpass endpoint from ending your presentation.
ADR-3
Tiles

PMTiles on static hosting, not a tile server. One archive file, HTTP range requests, served from the same CDN as the app.

No tile infrastructure to run, pay for, or have fall over mid demo. It also makes the offline mode (X04) close to free, because the archive can be cached.
ADR-4
Adapters

Every source implements one SourceAdapter contract with a declared status: live, cached, mock, or planned. Open-Meteo, OpenAQ, a recorded fixture, and the not yet available Punjab EPA feed are the same shape to everything above them.

This is what makes S04 and R01 structural rather than a claim on a slide. Adding EPA later is one new file, and you can prove it on stage by toggling a mock.
ADR-5
Observation

One canonical record for everything measured. { sourceId, metric, value, unit, h3, validAt, retrievedAt, confidence, licence, exportable }. Provenance and licence are fields on the record, not a page you write at the end.

R02 and R05 fall out of the data model for free, and R03 has somewhere to put uncertainty. If provenance is a field, an unattributed number becomes a type error rather than an oversight.
ADR-6
LLM boundary

The model never emits anything executable. Natural language compiles to a validated JSON intent checked against a whitelist of metrics, operators, and geometries. The app executes the intent; it never executes model output.

Removes the injection and denial of service risk from A01, and makes the whole feature testable against a fixed golden set instead of impressions.
ADR-7
Key boundary

Keyless sources are called from the browser; keyed sources go through a route handler. Open-Meteo, Overpass, and Nominatim direct. OpenAQ, AQICN, and the LLM behind the server.

Verified: Open-Meteo, Overpass, Nominatim, and HDX all return permissive CORS headers, so the client path genuinely works. OpenAQ returns 401 without a key and AQICN needs a token. Both must be server side, because a token in client code is a token you have published.
ADR-8
Reachability

Travel-time reachability is precomputed as sets, never routed at runtime. The cold path computes, for every hex, the set of hexes reachable within 5, 10, and 15 minutes by road, and stores it as reachability_h3.parquet.

OSRM runs only at build time under ADR-2, so there is no routing engine available when a user drops a what-if pin. Without this decision the what-if feature (D05) and the siting optimiser (D04) simply cannot work, because both need to recompute coverage interactively. With it, a what-if placement is a set union in the browser: no request, no routing engine, instant redraw. About 2,400 sets for one district, well under a megabyte compressed. Build this in the same step as the access surface, not later.
ADR-9
One scale

PM2.5 in micrograms per cubic metre is the one canonical air quality scale. Every adapter converts to it before emitting an Observation. AQI never reaches analytics, scoring, or the map.

Three scales arrive at this system. Open-Meteo returns concentration, AQICN returns a US EPA index from 0 to 500, and OpenAQ returns raw values per pollutant. Mixing them means a hex can be coloured on one scale and scored on another. Concentration wins because it is what the keyless always-available source returns and because it is a physical measurement rather than a country-specific index. The severity ramp and the Civic Access Score air bands then share one set of boundaries: 12, 35, 55, 150, 250. The legend prints both the concentration and the band name, because a resident recognises "hazardous" and a policymaker recognises the number.

The rule that keeps the demo alive

Every warm path adapter records its responses to data/fixtures/ the first time it succeeds. A single environment flag switches the whole registry to fixture mode. Rehearse the demo at least once in fixture mode with the laptop in airplane mode. If it works there, no venue wifi failure and no rate limit can take the presentation down.

05

User flows

Three people use this and they want different things in a different order. Design the entry point for the citizen, because they arrive with no context and no patience. The other two will tolerate more.

Citizen

Wants: is my air bad, is my street going to flood, where is the nearest clinic, and can I report the rubbish outside.

  • Lands on a map already centred on their location, no login
  • Sees one headline number and one sentence, not a dashboard
  • Taps through to the neighbourhood profile
  • Subscribes to alerts for their area
  • Submits a report in two taps

Official or councillor

Wants: which areas need attention this week, and something they can forward without editing.

  • Opens the ranked Civic Access Score table
  • Filters to their jurisdiction
  • Reads the generated situation brief
  • Checks report hotspots and response times
  • Exports the one page PDF summary

Planner or analyst

Wants: to test an intervention and get defensible numbers out.

  • Adjusts the score weights and watches the ranking move
  • Runs the siting optimiser for a facility type
  • Drops what-if pins and compares coverage
  • Opens two areas side by side
  • Pulls GeoJSON from the public API

The flow decision most teams get wrong

Do not open on an empty map with a layer panel. A first time visitor who sees fourteen toggles and no answer leaves. Open with one number, one sentence, one action for wherever they are, and let the full map be the second screen. This is the difference between a tool and a demo, and a judge notices it in the first three seconds.

06

Interface and experience

Two of the eight judging criteria live here, and this is where most civic data projects visibly fail. The governing idea: the map is not the product. The map is one view onto a set of answers, and every answer must exist without it.

6.1 Five principles specific to this platform

  1. The answer comes before the interface A resident opening this during smog season wants one sentence, not a control panel. Every screen leads with its conclusion and puts the controls that produced it underneath.
  2. Every number carries its people A reading alone is a measurement. A reading next to the population it affects is information. This is a layout rule, not just a data rule: the exposure count sits adjacent to the value at the same visual weight.
  3. Uncertainty is rendered, not hidden Lahore has few public sensors. Interpolated cells get hatching and reduced opacity, and cells with no nearby sensor are drawn as no data rather than smoothed over. A confident looking map of guesses is the failure mode here.
  4. Nothing important is only visual Every map layer has a table twin at a real URL. Severity is never carried by colour alone. The map is an accelerator for people who can use it, never the only route to an answer.
  5. Design for the worst device on the worst connection A 360px screen, a mid range Android, a throttled connection. The people most exposed to bad air and flooding are the least likely to be on fast unmetered data, so the low end is the real target, not a fallback.

6.2 Content rules for the whole platform

These are binding on interface copy, generated briefs, alert text, documentation, commit messages, and the pitch deck. Put them in CLAUDE.md and in the pull request template so they are enforced rather than remembered.

Never use em dashes

No em dash anywhere in the product or its documentation. Use a full stop when the second half is its own thought, a comma for an aside, a colon to introduce, or parentheses for a genuine aside.

  • They render inconsistently across the Latin and Urdu font stacks, and break awkwardly in RTL layout
  • Screen readers handle them unpredictably, sometimes as a pause and sometimes silently
  • They are a common tell of unedited machine generated text, which matters for a project whose briefs are model written
  • Enforce with a lint rule over source, message catalogues, and generated output

Never use emoji

No emoji in the interface, labels, legends, markers, alerts, generated text, README, or the deck. Use text labels, and where a graphic is needed use an inline SVG icon from one set.

  • Screen readers announce them by their full Unicode name, which turns a status chip into noise
  • They render differently on every platform, so a severity indicator becomes a different severity indicator on another device
  • Using emoji as a severity or category marker fails the colour and non text contrast requirements outright
  • They read as unserious on a civic tool that is asking officials to act on its numbers

How to write the copy instead

Name things the way a resident would, and say what happened rather than what the system did.

  • Not "PM2.5 concentration 214 µg/m³" alone, but "Air is hazardous today. 214, about nine times the safe level."
  • Not "no data", but "no sensor within 8 km of here"
  • Every error says what broke, what still works, and what to do next
  • Every estimated number says it is estimated in the same breath as the number
  • A control says exactly what will happen, and the confirmation uses the same verb

Why the ramp inverts between themes

In the light theme severity increases with darkness. In the dark theme it increases with luminance. The invariant being preserved is not hue, it is visual weight against the ground: the worst areas must be the ones your eye lands on first, and on a dark map a dark purple hexagon disappears. Both ramps stay perceptually ordered under deuteranopia and protanopia, and both are doubled with a text label in the legend and a hatch pattern for estimated cells, so hue is never the only carrier. Offer the official air quality colours as an opt in setting for users who already know that scale.

Major page divisions
  1. Base unit is 4px and nothing sits off the scale No 7px, no 15px, no 22px. If a value feels like it needs to be 18px, the answer is 16 or 24. A single off scale value is invisible; forty of them is why an interface looks amateur without anyone being able to say why.
  2. Container padding is one token at three breakpoints 16px below 768, 24px to 1200, 32px above. Set it once on the container and let every page inherit. Never let an individual screen set its own.
  3. Minimum 24px between any two unrelated groups If two blocks are not about the same thing, they get space-5 or more. Panels that violate this are the reason dashboards feel cramped even when nothing is technically overlapping.
  4. Panels never nest more than three levels deep Container, group, item. A fourth level means the information architecture is wrong, and each level of nesting eats padding on a 360px screen until the content column is unusably narrow.
  5. Empty space is load bearing on the Now screen The single headline number and its sentence own the top third of the viewport with nothing competing. Resist filling it. The generosity there is what makes the density of the map screen acceptable by contrast.
  6. The map is the only full bleed element Everything else respects the container. Map controls sit inset by 16px from the canvas edge, never flush.

Elevation

  • Three levels only: flat, raised, floating
  • Raised is a 1px border plus a barely visible shadow
  • Floating is for sheets, popovers, and the scrim
  • In dark mode elevation is a lighter surface, not a stronger shadow

6.6 Which features need their own place

Not everything deserves a screen, and the most common structural mistake is giving a feature a route when it should live beside the number it explains. Five decision rules, applied to all 32 core features.

  1. Would someone want to send this as a link? If yes it needs its own route. A neighbourhood profile a councillor forwards, a ranking table, an optimiser result. If it cannot be linked, it cannot be shared, and a civic tool that cannot be shared does not spread.
  2. Does it hold state that navigating away would destroy? Own route. The optimiser parameters, a comparison pair, adjusted score weights. Cramming these into a map panel means one stray click loses the work.
  3. Does it only make sense with a live map and a selection? Map panel. The what-if pin, the selection readout, the time scrubber. These are meaningless without the canvas behind them.
  4. Does it explain a single number? Inline, immediately beside that number. Provenance, uncertainty, the why-this-value explanation, the exposure count. Moving any of these to a separate page is how a system loses its credibility, because nobody navigates to check.
  5. Does it run without anyone watching? No interface at all. Verification, deduplication, clustering, alert dispatch, adapter polling. Surface the result, never the machinery.

Three model traps specific to this data

Random splits on time series. If you shuffle hours into train and test for M2 you will report a spectacular score and have learned nothing. Split by time, always, and hold out the most recent weeks. What has to happen before development

Beyond choosing features and reading the brief. These are the things that, left undone, surface at hour thirty when there is no time to fix them. The first one is not optional and is genuinely urgent.

Settle the pre-building question in writing, first

The rules say all work submitted must be created during the hackathon period. You are planning heavily in advance, which is good and almost certainly allowed, but planning, scaffolding, and pre-written code are three different things and only the first is unambiguously safe. Email the organisers now and get a written answer on: repository scaffolding, pre-downloaded and pre-cleaned datasets, pre-trained models, and the use of AI coding assistants. Keep the reply. This costs one email and removes the only risk on this page that can disqualify you no matter how good the build is.

  • Get every account and key issued and tested OpenAQ key, AQICN token, Copernicus Data Space account, Earth Engine project if you use it, a database, hosting, an LLM provider, and an SMS gateway if you commit to P04. A key that arrives by email approval on day two is a feature you did not ship.
  • Licensing, decided: MIT for code, ODbL for data OSM is ODbL, and its share-alike clause reaches derived databases. The public API (R04) publishes travel times computed from the OSM road graph plus facility locations lifted from OSM, which makes that export a derived database rather than a picture of one, so it carries ODbL. Share-alike does not reach your code: ODbL governs databases, not software. Dual licence, the standard civic-technology arrangement: MIT for the application, ODbL 1.0 for published exports and committed artifacts, CC-BY-4.0 for documentation. Both licence files are written and the full canonical ODbL text is appended to LICENCE-DATA. Two upstream sources restrict redistribution, checked against their own published terms. AQICN is display only: their Terms of Service say the data "can not be redistributed as cached or archived data", so those readings appear on the map and in no export. OpenAQ is conditional and machine readable: GET /v3/licenses returns a redistributionAllowed flag per licence, and the adapter gates on it. Neither the Pakistan Bureau of Statistics nor Open Data Pakistan publishes a site-wide licence, so terms are established per dataset or the file is excluded from export. This is why the Observation record carries a required exportable boolean: the licence question has to travel with the value rather than be remembered at the export endpoint.
  • Establish which admin level OSM actually carries Your single biggest data risk, and a thirty-minute Overpass query. Union council boundaries for Lahore are not reliably available as open geodata. Count complete polygons at admin levels 6, 7, 8 and 9 inside the district boundary, use the finest level with acceptable coverage, and print that level in the interface footer so the map never implies a precision the data does not have. Union councils are what the brief asks for; towns and tehsils are the fallback that reliably exists. Because the administrative layer is a config value rather than a hardcoded assumption, falling back one level changes nothing else in the system.
  • Count the sensors Query OpenAQ and AQICN for how many stations actually report in Lahore right now. The answer decides whether M1 is a real interpolation model or an honest uncertainty band over a forecast grid. Both are respectable; only one of them is what you should claim.
  • Verify Docker Desktop and WSL2 on every machine OSRM and tippecanoe are Linux binaries with no Windows-native path. This is an install, a reboot, and possibly a corporate policy problem, and it blocks the entire cold path. Check every laptop, not only the one that will run the ETL.
  • Decide where build artifacts live PMTiles plus the WorldPop clip plus the parquet files can cross GitHub's 100 MB per-file hard limit. Choose Git LFS or host them in object storage and fetch at build. Five minutes now, a bad hour at the first push.
  • Build unit, decided: Lahore District The whole district is gridded at H3 resolution 8, roughly 2,400 cells, so the demo's focus area is chosen by the data from the Civic Access Score ranking once the cold path lands, rather than guessed in advance. Opening on the worst-served area after ranking every area is a stronger demo than picking a neighbourhood up front, and it costs nothing extra because the grid already covers everything.
  • Set the timezone policy before the first adapter Asia/Karachi is UTC+5 with no daylight saving, and Open-Meteo returns GMT unless asked otherwise. Store UTC, render local, and request the local timezone so forecast hours align to local days. A naive local timestamp in the store is a five-hour bug that surfaces as the smog forecast being wrong by a day.
  • Write the sanity gates before the ETL Lahore district's population is roughly 11 million on the 2023 census. If your WorldPop clip sums to four, you clipped wrong. Put these assertions in etl/validate.py and fail the pipeline on them. A silently mis-clipped raster produces a beautiful map of nothing, and nobody catches it until a judge does.
  • Decide the privacy policy for citizen photos Reports will contain faces, number plates, and house numbers. The Code of Conduct forbids misusing personal data. Decide now: blur faces and plates automatically, strip EXIF beyond the coordinates you need, set a retention window, collect no names or phone numbers you do not use. Write it on the About page. Both an ethics obligation and an easy point on Real-World Application.
  • Agree the design system before the first component Tokens, spacing scale, and content rules from section 06 go into tokens.css, space.css, and CLAUDE.md on day zero. Retrofitting a spacing scale onto forty components at hour thirty is how teams end up shipping the inconsistent version.
  • Confirm the submission requirements Ask the organisers: presentation length, deck format, whether the repository must be public, whether a video is required, and how the demo is run: your laptop, their screen, or a shared machine. Design the demo for the actual constraint rather than discovering it in the queue.
  • Assemble the physical and human prerequisites A budget Android phone to test on. A fluent Urdu speaker to review X01 and M12, because machine translated Urdu that reads badly is worse than English. At least one person who has used MapLibre before, or an evening spent learning it before the clock starts.
  • Agree the working rules Branch naming, whether you review pull requests or push to main, who has deploy rights, when the code freeze is (three hours before judging, not thirty minutes), and who presents. Decide the freeze time before you are attached to a half finished feature.
  • Stand up the deployment on day zero An empty page deployed to a real URL in the first hour is worth more than a perfect local build. Deploy continuously from then on. Teams that leave deployment to the end demo from localhost, and localhost is where demos die.
  • Prepare the demo fallbacks A fixture mode run that works offline, a recorded screen capture of the full flow, a phone hotspot, and the laptop charger. In that order of usefulness.
  • Write the definition of done One line, agreed by everyone: a feature is done when it has a test, handles all seven states, works at 360px, has provenance on its numbers, exists in both locales, and appears in the demo script. Anything else is in progress, whatever the person building it says.

The traceability chain

Each feature ID from the feature plan should be followable in one direction with no gaps: feature, layer, source, model, placement, screen, route, file, test. If any feature cannot complete that chain, it is not designed yet, whatever it looks like on the map. Run the trace at each stage gate below. It takes fifteen minutes and it catches the two or three things that would otherwise be discovered during judging.

11
